### 2. Phase 1a isolation from 1b / 1.5

- **Intended coupling (fine):** shared `voice_text_utils`, shared `voice_tts` LRU, shared `TTS_API_KEY`, shared §6 cascade wording — all documented.
- **Hidden / blurry coupling:**
  - **§13 vs §3.3:** §13 locks HIGH leak to **live, unlocked browser session** and forbids queuing for next visit; §3.3 still floats `daily_sync.py` POST to `/api/events/speak` or `tts_pending` “implementation review.” That’s a **direct conflict** — cron/dashboard HTTP is not a “live browser session.”
  - **`POST /api/events/speak` + `{ text: ... }`:** If the browser supplies free-form `text`, backend must not treat it as authoritative for financial narration — server should **derive** sync-all strings (and ideally tightly constrain leak copy), else you get a **weak trust boundary** even same-origin.

---

### 3. `voice_text_utils` design

- **Strong:** Pure function, `len(result) <= cap`, sentence regex → accumulate until over cap → word fallback → hard chop; Unicode/codepoint-safe in Python; tests listed including idempotence.
- **Minor spec gap:** Inter-sentence joining (spaces vs empty) should be pinned so JAX/CFO/hub never diverge on whitespace around boundaries.

**Two-sentences-over-cap:** As written (“stop as soon as accumulated length would exceed cap”), taking the maximal prefix of **complete sentences** that stays ≤ cap is consistent with the example `"Sentence one."` at cap 30 — **acceptable**, though the prose could explicitly say “greedy prefix of full sentences under cap” to match implementers’ intuitions.

---

### 4. `TTS_API_KEY` startup guard — bypass?

- **Not “no bypass whenever unset” globally:** unset key + non-production → auth bypass can remain (§5.1). **Production-only** fail-fast is clear.
- **Residual bypass:** Production mis-set `ENVIRONMENT` (missing/wrong) could leave the old bypass behavior — worth treating as operational **must-fix** if Mike wants “no accidental open `voice_tts` on PGX.”

---

### 5. `X-Caller` logging vs privacy

- Values are **low sensitivity** (`jax`, `dashboard-events`). Doc correctly states **adapter-side logging first**; service ignores header until Phase 2.
- **Adequate for attribution** without embedding user content in headers — **yes**, provided logs stay `[TTS] caller=… status=…` without bodies (already implied).

---

### 6. Failure cascade — Claude on sensitive content?

- **TTS failure path:** No route from failed `/speak` → Claude/cloud — **good**.
- **User `/voice` path:** Stripping trigger then running **existing** `run_claude` means **any** sensitive user prompt can still reach Claude **before** TTS — that’s unchanged JAX semantics, not introduced by the adapter.
- **CFO events:** Server-generated short strings only — **no** LLM in the Phase 1a narration path.
